# 产品定位与开发需求

## 1. 一句话定位

Cloud Agent Platform 是一个面向 AI 应用开发与平台工程学习的开源执行底座：它把模糊需求和代码仓库转化为
受预算、策略和沙箱约束的 Agent 工作，并把过程事件、错误、用量和产物完整返回。

## 2. 给谁使用

### 核心用户

**AI 应用工程师**

- 需要学习或搭建 Agent Loop、function calling、工具注册表和 Provider Adapter。
- 不想从一个不可取消、不可观测的脚本开始。
- 需要一个可以替换模型、队列、存储和沙箱的模块化基线。

**平台工程师与技术负责人**

- 需要评估任务状态机、幂等、租约、取消、预算和审计等控制面问题。
- 需要向团队解释“模型推理”和“不可信代码执行”为什么必须分层。
- 需要一条从本地 MVP 演进到 PostgreSQL、Redis、对象存储、Temporal 和 Kubernetes 的路径。

**软件工程师面试候选人和学习者**

- 需要把一个模糊 Cloud Agent 场景题拆成需求、架构、安全、实现、测试和演示。
- 需要展示真实代码，而不只是画图或堆叠框架名词。
- 需要能客观说明 MVP 取舍、限制与生产化缺口。

### 邻近用户

**产品经理、创业者和交付顾问**可以使用需求挖掘页面，把“做一个物流司机排班软件”这类输入逐轮补全为可评审的
软件设计报告。当前 Demo 对物流场景有确定性模板；使用 OpenAI Provider 时可处理更开放的需求，但输出仍需要
业务与技术负责人确认。

## 3. 要解决的问题

传统 LLM 工具 Demo 常见四个断点：

1. 只展示一次模型调用，没有任务生命周期和失败语义；
2. 直接在宿主机执行命令，没有可信边界和资源上限；
3. 把聊天记录当审计日志，无法区分公开事件与模型私有推理；
4. 生成一个文件就宣称完成，没有幂等、取消、产物去重和清理保证。

本项目将这些问题拆成控制面、执行面和证据面：

- 控制面负责身份入口、任务、状态、队列、租约和取消；
- 执行面负责仓库、模型、工具、沙箱和预算；
- 证据面负责事件、用量、错误和内容寻址产物。

## 4. 核心业务场景

### 场景 A：需求发现

输入：模糊的软件想法和可选前置条件。
过程：创建会话 → 多轮澄清 → 用户补充 → 准备完成 → 生成报告。
输出：需求摘要、用户与角色、范围、流程、非功能需求、风险、假设、未决问题和开发建议。

### 场景 B：仓库分析

输入：自然语言任务、Git 仓库、ref 和预算。
过程：创建任务 → 队列 → 租约 → 准备仓库 → Agent/工具循环 → 收集产物 → 清理。
输出：任务终态、事件、用量和报告。

### 场景 C：Agent Platform 教学与评审

输入：架构评审或二次开发目标。
过程：沿代码导览检查控制面、执行面、契约和测试。
输出：可验证的设计取舍、扩展点和风险清单。

## 5. MVP 功能需求

- FR-01：用户可提交自然语言任务和仓库引用，服务返回稳定 Task ID。
- FR-02：重复幂等请求不得创建重复任务；内容冲突必须显式拒绝。
- FR-03：任务遵循合法、不可逆的终态状态机。
- FR-04：Worker 使用队列、可见性超时、租约和心跳领取执行权。
- FR-05：Agent 在总时间、轮次、token、命令时间和输出大小限制内运行。
- FR-06：所有工具调用先经过结构校验和策略授权，再由 SandboxSession 执行。
- FR-07：排队和运行中的任务均可取消，取消传播到工具协程和进程树。
- FR-08：平台只记录公开行动摘要、工具事件、状态和用量，不保存私有思维链。
- FR-09：文本产物可列出、校验哈希并下载，重复提交保持幂等。
- FR-10：用户可通过多轮对话把模糊需求整理为软件设计报告。

完整可追踪需求见 [软件需求规格说明书](sdlc/02-software-requirements-specification.md)。

## 6. 非功能需求

- **安全**：默认禁网、非 root、最小权限、路径与符号链接边界、秘密脱敏。
- **可靠性**：at-least-once + 业务幂等；租约丢失不能覆盖有效终态。
- **可观测性**：JSON 日志、任务/attempt 关联、单调事件和用量摘要。
- **可移植性**：Python 3.10–3.12；Windows 与 Linux CI；本地和容器启动。
- **可扩展性**：Provider、Sandbox、EventSink、ArtifactStore 等通过 Protocol/Adapter 解耦。
- **可测试性**：离线 Demo、MockTransport、单元/集成/E2E/安全测试均不依赖真实付费调用。

## 7. 成功指标建议

当前仓库是技术 MVP，以下指标用于下一阶段内部试用，而非已经达成的生产 SLO：

- 代表性仓库任务成功率与失败原因分布；
- P50/P95 排队、准备、模型、工具和总耗时；
- 每个成功任务的 token、模型费用和工具调用数；
- 取消完成时间和孤儿进程/沙箱数量；
- 需求报告的事实覆盖率、未确认假设率和人工返工率；
- 路径逃逸、秘密泄露、越权工具和网络访问的阻断率；
- Worker 崩溃后的恢复成功率与重复产物率。

## 8. 不做什么

- 当前不自动提交代码、创建 PR、部署服务或写入生产系统。
- 当前不支持私有仓库凭证，不允许把个人 Token 放进仓库 URL。
- 当前内存存储不提供重启恢复、多实例一致性或生产 SLA。
- 当前 Docker 隔离不承诺抵御任意内核级恶意工作负载。
- 当前单 Agent Runtime 不应宣传为已经实现的多 Agent 开发团队。

明确非目标能让项目的开源叙事更可信：Star 的价值来自可验证的工程细节，而不是更大的功能口号。
