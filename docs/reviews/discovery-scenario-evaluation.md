# 多轮需求发现 15 场景评测报告

## 1. 结论

本次评测对当前 `DemoDiscoveryAssistant` 执行了 15 个模糊需求、45 轮用户回答、
15 次报告生成和 15 次受认证下载。其中包含 3 个电商业务：库存防超卖、商家对账结算、退换货。

结论必须分为两层：

- 技术生成通过：15/15。所有场景都完成 `DISCOVERY → READY → FINALIZED`，回答被保留，
  报告可下载，没有回退为 TODO 扫描报告。
- 开发可实施质量通过：1/15。只有专门实现领域模板的物流司机排班达到质量门；
  其余 14 份使用通用报告骨架，没有把领域信息转化为足够具体的数据模型、API、状态机和验收用例。

因此当前版本适合演示“多轮会话和产物链路”，但不能宣称已经具备跨领域需求分析能力。

## 2. 可复现方式

场景、三轮回答和评分器位于 `scripts/run_discovery_evaluation.py`。

```powershell
.\.venv\Scripts\python.exe scripts\run_discovery_evaluation.py --summary-only
```

本次实测摘要：

```json
{
  "scenarioCount": 15,
  "conversationRounds": 45,
  "ecommerceCount": 3,
  "technicalPassed": 15,
  "qualityPassed": 1,
  "averageDurationMs": 22,
  "averageReportChars": 1048
}
```

这里的 22ms 是离线确定性 Demo 的本机平均处理时间，不代表真实 LLM 延迟。

## 3. 评测口径

### 3.1 技术生成门

每个场景必须同时满足：

1. 创建会话返回 HTTP 201。
2. 三轮回答均返回 HTTP 200。
3. 第三轮后状态为 `READY`。
4. 生成后状态为 `FINALIZED`。
5. 报告产物可以通过授权 URL 下载。
6. 三轮用户回答均原样保存在报告中。
7. 报告不是旧的 `TODO Report`。

### 3.2 开发可实施质量门

报告至少 1,000 字，并覆盖以下六个维度中的五个以上：

1. 用户角色、产品边界与 MVP 范围。
2. 核心流程、业务规则、异常和状态流转。
3. 领域数据模型、关键实体和一致性约束。
4. 可落地技术架构与主要 API。
5. 安全、隐私、性能、可用性和恢复目标。
6. 可自动测试、可由业务方签字的验收标准。

此外，报告的“生成设计部分”必须出现至少四个领域关键词，不能只在用户回答摘录里出现。

## 4. 场景清单与结果

### 4.1 三个电商场景

#### ECOM-OVERSELL：库存防超卖

- 模糊需求：做一个能减少超卖的电商库存软件。
- 三轮补充：20 万 SKU、多渠道共享库存、秒杀 3,000 TPS；预占/扣减/释放；
  对接 ERP/WMS，P99 小于 100ms。
- 技术生成：通过。
- 开发质量：8/20，未通过。
- 缺失：库存账户与库存流水模型、预占状态机、幂等键、渠道库存同步、
  超时释放、最终一致性和热点 SKU 方案、可执行 API 契约。

#### ECOM-SETTLEMENT：商家对账结算

- 模糊需求：给平台做一个商家对账结算系统。
- 三轮补充：10 万商家、日 200 万订单；订单/退款/佣金/补贴/券/罚款；
  结算批次幂等、禁止重复付款、数据保留七年。
- 技术生成：通过。
- 开发质量：8/20，未通过。
- 缺失：会计分录与账单行模型、账期与批次状态机、差异申诉、冲正而非覆盖、
  付款幂等、双录复核、审计和资金风险控制。

#### ECOM-RETURNS：退换货

- 模糊需求：做一个电商退换货软件。
- 三轮补充：仅退款/退货退款/换货；收货质检后退款；订单、支付、物流、WMS 和风控集成。
- 技术生成：通过。
- 开发质量：8/20，未通过。
- 缺失：售后单、逆向物流、质检、退款和换货履约状态机；重复退款防护；
  部分退款、拒收、换货缺货和超时自动关闭等异常路径。

三个电商报告都成功生成文件，但不能直接交给研发估时和编码。

### 4.2 物流司机排班

- 模糊需求：设计一个物流司机排班用的软件。
- 三轮补充：100 名司机、80 辆车；驾照、车型、驾驶休息规则；TMS/GPS；
  首次求解 60 秒、局部重排 10 秒。
- 技术生成：通过。
- 开发质量：20/20，通过。
- 原因：当前 Demo 为这个场景实现了专用报告，包含角色、硬/软约束、
  OR-Tools 求解策略、领域模型、API、审计、安全、性能和 MVP 验收标准。
- 遗留：业务法规仍需适用地区的合规专家确认；报告可用于原型和技术 Spike，
  不能直接视为最终劳动法规实现依据。

### 4.3 其他 11 个场景

以下场景技术生成全部通过，开发质量均为 8/20：

- SaaS 客服工单自动分流。
- 工厂设备维护。
- 医院挂号排队。
- 学校自动排课。
- 物业报修派单。
- 连锁餐饮自动补货。
- 仓库拣货优化。
- 工地安全巡检。
- 自动安排面试。
- 农田智能灌溉。
- 老人上门服务调度。

共同缺口不是“用户信息不足”，而是 Demo 报告器只把三轮回答复制到“已确认信息”，
后续仍输出通用 CRUD/模块化单体建议。它没有执行真正的领域建模与方案综合。

## 5. 开发角度评估

### 5.1 已经做好的部分

- 会话状态清楚：`DISCOVERY / READY / FINALIZED`。
- 三轮历史保真，报告能够追溯输入。
- 租户 Bearer 隔离和受认证下载已存在。
- 输入长度、最大轮数、报告大小和只读终态有边界。
- 离线 Demo 可重复，不依赖费用和网络，适合 CI 冒烟测试。
- 物流样例展示了目标报告应该达到的细度。

### 5.2 阻止研发开工的关键缺口

#### 缺口 A：没有结构化需求快照

当前真相源是聊天文本。研发无法稳定查询“确认了什么、谁确认、何时确认、证据在哪一轮”。
需要新增 `RequirementSnapshot`：

- `actors`：角色、权限、目标和痛点。
- `workflows`：主流程、异常、审批和状态机。
- `rules`：硬约束、软约束、优先级和法规来源。
- `entities`：实体、关系、唯一键、生命周期和数据所有者。
- `integrations`：系统、协议、方向、鉴权、频率和失败策略。
- `nonFunctional`：规模、延迟、吞吐、可用性、RPO/RTO、安全和保留期。
- `assumptions`：默认假设、风险、负责人和失效条件。
- `openQuestions`：阻塞级别、截止时间和决策人。
- `acceptanceCriteria`：Given/When/Then、指标阈值和证据要求。
- `provenance`：每个字段对应的会话消息、用户确认或领域来源。

#### 缺口 B：没有领域分析和架构分工

一个模型同时提问、总结、架构和自评容易产生模板化结果。应该由不同 Agent 分阶段负责，
用结构化产物交接，而不是互相发送自由文本。

#### 缺口 C：`FINALIZED` 不代表质量通过

当前只要报告文件成功写入就进入 `FINALIZED`。建议拆分：

```text
READY_FOR_DESIGN
  → DESIGNING
  → REVIEWING
  → NEEDS_CLARIFICATION / NEEDS_APPROVAL
  → QUALITY_PASSED
  → FINALIZED
```

Reviewer 必须检查需求覆盖、矛盾、假设、领域深度、安全、可测试性和引用证据。

#### 缺口 D：没有报告到开发任务的追踪关系

报告章节应生成 Epic、Story、API、数据迁移、威胁模型和测试任务，
每个任务带 `requirementIds`。需求变更时能够计算受影响任务，而不是重写整份文档。

#### 缺口 E：进程内会话不可生产使用

服务重启会丢失会话元数据。生产需要 PostgreSQL 持久化、版本号、租户索引、
乐观锁、幂等消息写入和审计事件；大报告进入 S3/MinIO。

## 6. 优先改进建议

### P0：让跨领域报告真正可开发

1. OpenAI Provider 模式启用结构化需求提取，不再使用通用 Demo 报告作为生产结果。
2. 为每轮回答更新 `RequirementSnapshot`，对冲突字段要求用户确认。
3. 引入 Product、Domain、Architecture、Security、QA Reviewer 五个 Agent。
4. 报告生成后执行确定性 Schema 检查和 LLM Judge；低于阈值自动退回补问。
5. 报告必须带需求覆盖矩阵和未决问题，未决 P0 不允许进入开发计划。

### P1：提高可靠性和可运营性

1. PostgreSQL 持久化会话、快照、决策、Agent Run 和评分。
2. 使用 Redis Streams 或 Temporal 管理长流程、重试、等待用户和恢复。
3. 增加真实模型评测集：每个领域至少 20 个模糊需求，保留人工黄金标准。
4. 记录每个 Agent 的 token、耗时、重试、质量分和失败原因。
5. 对医疗、金融、劳动法规等高风险内容强制人审，不允许模型自行确认法规。

### P2：从设计进入多 Agent 开发

1. Planner 将已批准设计拆为带依赖的任务 DAG。
2. 后端、前端、Runtime、安全和测试 Agent 在隔离分支/工作区并行工作。
3. Integration Agent 合并；QA、安全和可靠性 Reviewer 独立验收。
4. 外部写入、部署、PR、生产数据和费用操作必须经过审批节点。

## 7. 建议质量阈值

上线前至少满足：

- 技术生成通过率 100%。
- 结构覆盖率至少 90%。
- 领域关键词与实体/规则人工抽检通过率至少 85%。
- 所有 P0 需求具有验收标准和来源。
- 未确认假设不得被标记为用户决定。
- 安全 Reviewer 无未关闭 Critical/High。
- 同一输入重复运行三次，关键事实和接口契约保持稳定。
- 真实业务专家对报告给出“可估时、可拆任务”的结论。

## 8. 工程回归补充

全量回归曾暴露 Windows 上取消任务后的瞬时文件句柄占用：旧实现使用
`shutil.rmtree(..., ignore_errors=True)`，可能静默留下 attempt 工作目录。现已改为有限退避重试；
目录不存在视为幂等成功，持续失败则上抛并由 Worker 映射为 `CLEANUP_FAILED`，不会把清理失败伪装成成功。

修复后通过：完整 pytest 回归、Ruff lint、Ruff format、mypy，以及取消任务后进程树终止和工作区销毁的定向测试。
