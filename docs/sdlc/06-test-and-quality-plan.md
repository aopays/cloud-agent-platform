# 测试与质量计划

- 文档版本：1.0
- 状态：`DRAFT`
- 负责人：QA Lead；各模块工程师对单元与组件质量负责

## 1. 质量目标

验证系统不仅“能生成结果”，还能够在重复投递、取消、超时、恶意输入、模型波动和基础设施故障下保持安全、
一致、可恢复和可审计。测试结论必须区分执行成功、技术正确、业务可用和发布批准。

## 2. 测试层次

- 静态门：格式、lint、类型、依赖、secret、许可证、SBOM 和 IaC。
- 单元测试：状态机、预算、Schema、路径、策略、重试、脱敏和纯领域规则。
- 组件测试：API、Repository、Queue、Runtime、Provider、Sandbox 和 Artifact adapter。
- 契约测试：OpenAPI、事件 Schema、数据库迁移、模型工具格式和消费者兼容。
- 集成测试：API→队列→Worker→Runtime→Sandbox→Artifact 完整组合。
- E2E：浏览器/SDK 的真实用户流程、错误恢复和授权边界。
- 非功能：性能、容量、耐久、混沌、灾备、可访问性和成本。
- AI Eval：事实忠实、需求覆盖、领域深度、工具选择、可重复性和安全拒绝。
- UAT：业务方使用真实但去敏任务确认可用性。

## 3. 核心测试场景

### 功能

- `CAP-TC-001` 创建任务、事件完整、产物可授权下载、终态为 SUCCEEDED。
- `CAP-TC-002` 相同幂等键重复创建返回同一任务；请求体不同返回冲突。
- `CAP-TC-003` 排队取消、准备中取消、运行中取消均终止且没有工作区残留。
- `CAP-TC-004` 模型超时、工具超时、墙钟超时分别映射稳定错误。
- `CAP-TC-005` Worker 崩溃后租约过期，恢复扫描创建合法重试 attempt。
- `CAP-TC-006` 15 个模糊需求完成三轮对话并生成报告，三类电商必须覆盖领域模型。
- `CAP-TC-007` P0 冲突存在时报告不能进入 QUALITY_PASSED。

### 安全

- `CAP-TC-020` `..`、绝对路径、符号链接、TOCTOU 和编码绕过不能逃出工作区。
- `CAP-TC-021` shell metacharacter、超长 argv、fork bomb、输出洪泛和后台进程受控。
- `CAP-TC-022` 默认禁网；DNS、IPv4/IPv6、重定向和 metadata service 绕过失败。
- `CAP-TC-023` 恶意仓库 README 中的 Prompt Injection 不能扩大工具权限。
- `CAP-TC-024` API key、Git token、Authorization 和常见密钥格式不进入事件、错误和产物。
- `CAP-TC-025` 跨租户枚举、下载、取消和事件查询均被拒绝且不泄漏存在性。

### 可靠性

- `CAP-TC-040` 消息重复 100 次只产生一个合法终态和逻辑产物。
- `CAP-TC-041` 状态事件和 Runtime 事件并发时 sequence 无冲突、无丢失。
- `CAP-TC-042` PostgreSQL、Redis、对象存储和模型短暂故障后符合重试策略。
- `CAP-TC-043` 清理短暂失败重试；持续失败进入 CLEANUP_FAILED 并触发告警。
- `CAP-TC-044` 滚动发布期间运行中工作流不丢失、不重复副作用。

## 4. 性能与容量

- API：任务创建/查询在 1x、2x 和峰值负载下测 P50/P95/P99、错误率和饱和度。
- 队列：测排队时延、租约吞吐、恢复扫描、重复率和死信增长。
- Sandbox：测冷启动、并发启动、CPU/内存/PID/磁盘限制和销毁时延。
- 模型：按模型和 Prompt 记录 TTFT、总时延、token、重试和成本。
- Soak：以 60% 峰值运行 24 小时，检查内存、连接、孤儿进程和存储增长。

Beta 的初始门槛采用 SRS 中 NFR；达到 Production 前需要基于真实任务分布重新校准。

## 5. AI 质量评测

评测集至少包含 20 个仓库任务、15 个需求发现场景、Prompt Injection、工具误用、矛盾需求和高风险拒绝。每个样本
保存输入、允许事实、禁止行为、黄金结构和评分规则。评分组合：确定性 Schema/覆盖规则、领域关键词和实体检查、
独立 LLM Judge、人工盲评。模型或 Prompt 变更必须与基线比较质量、延迟、成本和拒绝率；不能只看平均分。

当前 15 场景结果为技术生成 15/15、开发质量 1/15，因此只能证明会话和产物链路，不证明跨领域设计能力。

## 6. 测试环境和数据

- Local：离线 Demo、可信本地 adapter、快速单元测试。
- CI：Mock Provider、Docker 策略测试、临时 PostgreSQL/Redis/MinIO。
- Staging：与生产同构、隔离账户、合成仓库和无真实凭证数据。
- Security Lab：隔离网络、恶意镜像/仓库和更严格访问控制。
- Production Canary：仅批准租户和任务，最小比例、完整监控和一键回滚。

测试数据使用合成或去标识化内容。禁止把真实密钥、客户私有仓库和生产个人数据复制到开发/CI。

## 7. 缺陷分级和退出条件

- Critical：跨租户、RCE 逃逸、凭证泄漏、不可恢复数据破坏；立即停止发布。
- High：核心流程不可用、终态错误、取消失效、审计缺失；发布前清零。
- Medium：有明确绕行的功能或可观测问题；必须有负责人和截止版本。
- Low：不影响核心目标的体验问题；进入 backlog。

G4 退出条件：Critical/High 为零；P0 测试 100% 通过；完整回归稳定三次；性能、安全、恢复和 UAT 通过；
Flaky 测试有明确隔离和修复计划，不能通过反复重跑掩盖。

## 8. 测试报告

每次发布报告必须记录构建版本、环境、范围、命令、通过/失败/跳过、缺陷、风险、性能、AI 评测变化、例外和
QA 结论。跳过测试需要原因、影响和批准人；“本机不能运行”不是生产验证证据。
