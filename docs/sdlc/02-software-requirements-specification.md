# 软件需求规格说明书（SRS）

- 文档版本：1.0
- 状态：`DRAFT`
- 需求标识前缀：`CAP-FR`、`CAP-NFR`、`CAP-SEC`

## 1. 系统上下文

系统边界内包括 Web/API、需求发现、任务服务、编排器、队列、Worker、Agent Runtime、工具策略、Sandbox、
事件、产物和审计。系统边界外包括身份提供商、Git 服务、OpenAI/其他模型、对象存储、通知系统和企业观测平台。

## 2. 功能需求

### 2.1 身份、租户与授权

- `CAP-FR-001`：系统必须认证用户并把请求绑定到 tenant、user 和 request ID。
- `CAP-FR-002`：租户只能读取自己的会话、任务、事件和产物。
- `CAP-FR-003`：管理员必须可以配置模型、工具、仓库域名、预算和并发配额。
- `CAP-FR-004`：高风险操作必须创建有时效、可撤销、范围明确的审批记录。

### 2.2 需求发现

- `CAP-FR-010`：用户可以提交 1–20,000 字符的模糊需求及前置条件。
- `CAP-FR-011`：系统应每轮选择 3–5 个信息增益最高的问题。
- `CAP-FR-012`：每轮回答必须更新版本化 RequirementSnapshot，并记录字段来源。
- `CAP-FR-013`：系统必须区分已确认事实、假设、冲突、待确认问题和业务决策。
- `CAP-FR-014`：P0 决策未解决时系统不得把报告标为质量通过。
- `CAP-FR-015`：报告必须覆盖范围、流程、实体、状态、API、NFR、安全、测试和未决问题。
- `CAP-FR-016`：用户可以查看会话历史、生成报告并下载经过授权的产物。

### 2.3 任务生命周期

- `CAP-FR-020`：创建任务必须支持幂等键，同一租户相同键和相同请求返回同一任务。
- `CAP-FR-021`：任务状态必须遵守冻结状态机，终态不可逆。
- `CAP-FR-022`：队列采用 at-least-once 语义，重复投递不能导致重复终态或重复逻辑产物。
- `CAP-FR-023`：Worker 必须使用有心跳和可见性续期的租约声明 attempt。
- `CAP-FR-024`：用户取消排队或运行任务后，模型请求、工具协程和沙箱进程树必须停止。
- `CAP-FR-025`：超时、预算耗尽、策略拒绝、清理失败和内部错误必须有稳定错误码。

### 2.4 Agent Runtime 与工具

- `CAP-FR-030`：Runtime 必须支持可替换 LLM Provider 和结构化工具调用。
- `CAP-FR-031`：每次工具调用必须通过 Schema、权限、路径和预算校验。
- `CAP-FR-032`：Runtime 必须限制总时长、轮次、输入/输出 token、工具时长和输出字节。
- `CAP-FR-033`：系统必须检测重复工具调用、无进展循环和重复失败。
- `CAP-FR-034`：模型瞬时错误可有限重试，非瞬时错误不得无限重试。
- `CAP-FR-035`：Runtime 不能直接在 API 或 Worker 宿主机执行模型生成的命令。

### 2.5 仓库与沙箱

- `CAP-FR-040`：仅允许配置根目录内的 `file://` 或 allowlist 域名的无凭证 HTTPS 仓库。
- `CAP-FR-041`：私有仓库必须使用任务级短期凭证，凭证不得进入模型上下文和日志。
- `CAP-FR-042`：每个 attempt 必须使用独立工作区，任务结束后销毁进程和目录。
- `CAP-FR-043`：生产沙箱默认非 root、禁网、只读根文件系统、移除 capabilities 和 Docker socket。
- `CAP-FR-044`：文件工具必须防止绝对路径、`..`、符号链接和竞态逃逸。
- `CAP-FR-045`：命令必须使用 argv-only，不允许 shell 拼接，并限制 CPU、内存、PID、磁盘和时间。

### 2.6 事件、产物与审计

- `CAP-FR-050`：attempt 内事件 sequence 必须原子、严格递增、追加写入。
- `CAP-FR-051`：用户可观察状态、模型、工具、预算、错误和产物事件，但看不到私有思维链。
- `CAP-FR-052`：大输出必须存入对象存储；事件只保存摘要、哈希和 artifact ID。
- `CAP-FR-053`：产物下载必须鉴权或使用短期签名 URL，默认禁止公开访问。
- `CAP-FR-054`：审计记录必须包含主体、租户、动作、资源、策略结果、时间和 request ID。

## 3. 非功能需求

- `CAP-NFR-001 可用性`：Production v1 月度 API 可用性目标 99.9%，不含预先公告维护。
- `CAP-NFR-002 性能`：正常负载下创建任务 P95 小于 500ms，查询 P95 小于 300ms。
- `CAP-NFR-003 排队`：有可用容量时 95% 的任务在 30 秒内开始准备。
- `CAP-NFR-004 取消`：95% 运行中任务在取消请求后 5 秒内终止活动进程。
- `CAP-NFR-005 容量`：Beta 支持 50 并发任务；v1 支持单区域 500 并发并可水平扩展。
- `CAP-NFR-006 耐久性`：已提交任务、事件和产物元数据在进程重启后不得丢失。
- `CAP-NFR-007 恢复`：控制面 RPO ≤ 5 分钟、RTO ≤ 30 分钟；产物按客户等级定义。
- `CAP-NFR-008 可观测性`：关键路径必须具有日志、指标和 trace，并支持 tenant/task 关联。
- `CAP-NFR-009 可维护性`：公共契约版本化；核心模块 mypy strict；新增行为有自动化测试。
- `CAP-NFR-010 成本`：任务级成本可归因，预算超限时终止并产生事件。
- `CAP-NFR-011 可访问性`：管理和需求发现页面目标达到 WCAG 2.1 AA 的核心交互要求。
- `CAP-NFR-012 兼容性`：API 采用向后兼容版本策略，消费者必须忽略未知可选字段。

## 4. 关键用例

### UC-01 创建并执行仓库分析任务

前置：用户已认证，仓库在允许范围，租户配额充足。主流程：验证请求；以幂等事务创建 task/attempt/outbox；
Worker 获取租约；准备仓库和沙箱；Runtime 循环调用模型与工具；保存事件和产物；清理并提交终态。替代流程包括
仓库拒绝、配额不足、模型超时、工具失败、租约丢失、用户取消和清理失败。

### UC-02 三轮需求发现

前置：用户已认证。主流程：创建会话；系统给出第一轮问题；用户回答；更新快照；继续两轮；并行执行领域、
产品、架构、安全和 QA 分析；若质量通过则生成报告。若有 P0 冲突，状态进入 `WAITING_FOR_USER`。

### UC-03 下载产物

系统验证 tenant 和 artifact 所有权，检查保留期和恶意内容扫描状态，生成短期下载 URL，记录审计。不存在、越权、
过期和隔离中的产物统一返回不泄漏资源存在性的安全错误。

## 5. 需求优先级

- Must：租户隔离、任务状态机、预算、取消、工具策略、沙箱、事件、产物鉴权、持久化和审计。
- Should：多 Agent 需求快照、实时事件、私有仓库、质量门、成本面板和灾备。
- Could：多区域主动-主动、客户自定义 Agent、插件市场和自动 PR。
- Won't for v1：无审批生产部署、通用浏览器自治和无限互联网访问。

## 6. 未决业务决策

- 目标云和首发区域；数据驻留要求。
- 私有仓库供应商和短期凭证方案。
- 模型数据保留政策及允许的模型列表。
- 产物默认保留期、客户自定义范围和删除 SLA。
- v1 是否允许写代码、创建草稿 PR，以及批准人模型。
- Beta 并发、单任务成本和月度预算的商业上限。

这些问题必须在 G1 或相关功能进入开发前由 Product Owner、Security 和 Sponsor 确认。
