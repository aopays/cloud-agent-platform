# 产品与业务需求文档（PRD）

- 文档版本：1.0
- 状态：`DRAFT`
- 产品：Cloud Agent Platform
- 目标版本：Internal Beta / Production v1

## 1. 背景与问题

企业研发人员经常需要把自然语言目标转换为一系列可审计的代码分析、文件修改、测试和报告操作。直接在开发者
电脑运行自治 Agent 会带来凭证泄漏、宿主机破坏、资源失控、过程不可追踪和多人协作困难。另一个上游问题是，
业务方通常只给出十几个字的模糊需求，团队在没有形成清晰范围和验收标准前就开始编码。

本产品提供两条连续价值链：

1. 从模糊需求出发，通过多轮会话和专业 Agent 形成结构化需求及软件设计报告。
2. 将批准的任务放入云端隔离环境，由受预算和策略约束的 Agent 执行，并返回事件、结果和产物。

## 2. 产品愿景

让企业团队可以像委派给一个受治理的远程研发团队一样委派 AI 工作：输入目标，观察过程，在需要人类决策时
审批，最后获得可验证、可下载、可追踪的交付物。

## 3. 目标用户

- 业务产品经理：从模糊想法形成范围、流程、验收标准和未决问题。
- 软件工程师：执行仓库分析、测试、文档、受控修改和技术调研。
- Tech Lead：拆分任务、控制并行开发、审核架构和集成结果。
- QA/安全人员：查看事件、工具调用、测试证据和策略拒绝。
- 平台管理员：管理租户、配额、模型、工具策略、沙箱镜像和成本。
- 合规/审计人员：按租户、任务和时间检索不可抵赖的操作记录。

首个商业落点是 20–200 人的研发团队和内部 AI 平台团队，不面向没有工程治理能力的普通消费者。

## 4. 核心价值指标

- 需求澄清：80% 的内部需求在 3–5 轮后形成可评审的结构化快照。
- 任务成功：受支持的只读仓库任务成功率至少 95%。
- 开发效率：常规代码分析与报告任务的人工作业时间降低至少 50%。
- 可追踪性：100% 的模型调用、工具调用、状态变化和产物有公开事件或审计记录。
- 安全：生产环境无未授权宿主命令执行、跨租户读取和明文凭证泄漏。
- 质量：所有 P0 需求具有来源、验收标准、实现模块和测试证据。

指标应在 Beta 前建立基线，不能把 Demo 的本地 22ms 响应时间当作生产性能数据。

## 5. 产品范围

### 5.1 As-Is MVP

- 创建、查询、取消任务；获取事件和产物。
- 输入自然语言任务、仓库 URL 和预算限制。
- Demo Provider 与 OpenAI Responses Provider。
- 文件列举、读取、搜索、受控写入、命令执行和结果提交工具。
- 本地可信 Sandbox 与 Docker Sandbox 策略。
- 三轮需求发现和 Markdown 软件设计报告。
- 开发 Bearer Token、单进程存储和本地产物目录。

### 5.2 Next：Internal Beta

- PostgreSQL 持久化、Redis/Temporal 工作流、S3/MinIO 产物。
- 企业 OIDC、租户 RBAC、配额、幂等、审计查询。
- 结构化 `RequirementSnapshot` 和多 Agent 需求分析。
- 任务实时 SSE、Worker 心跳、重试、死信和恢复扫描。
- 真实 Docker 隔离测试、镜像签名、依赖和漏洞扫描。
- 质量评分、人工审批和报告到开发任务的追踪。

### 5.3 Target：Production v1

- 多区域控制面、弹性 Worker 池、强隔离运行时。
- 组织级工具和模型策略、私有仓库短期凭证注入。
- gVisor/Kata/Firecracker 隔离选项和网络出口代理。
- 多 Agent 开发 DAG、独立工作区、代码集成与审查。
- SLO、成本归因、灾备、数据保留和合规审计。

## 6. 非目标

- v1 不允许 Agent 无审批部署生产、付款、删除业务数据或合并主分支。
- v1 不承诺替代产品经理、架构师、安全专家或法律意见。
- 不持久化模型私有思维链，只记录面向用户的行动摘要和证据。
- 不支持任意互联网访问；网络必须通过声明式 allowlist 和出口代理。
- 不把 Docker 本身表述为可对抗任意内核级恶意代码的最终安全边界。

## 7. 关键用户旅程

### 旅程 A：模糊需求到设计报告

用户输入“设计一个物流司机排班软件”和前置条件。系统识别信息缺口，每轮询问最高价值的问题；用户回答规模、
约束、集成和性能后，系统生成结构化需求快照。Domain、Product、Architecture、Data/API、Security 和 QA Agent
分别产出专业分析。若存在阻塞问题则回到用户；质量通过后生成报告和追踪矩阵。

### 旅程 B：仓库分析

用户提交仓库和“找出所有 TODO 并生成报告”。API 创建任务，队列投递，Worker 获取租约，准备只读仓库，创建
沙箱，Runtime 调用模型和受控工具。用户查看事件并下载报告；失败时获得安全、可操作但不泄密的错误。

### 旅程 C：受控代码修改

用户授权写入并定义测试命令。Agent 在隔离分支工作区修改文件、运行测试并生成补丁。安全或质量门禁失败时不创建
外部 PR；通过后由人类批准发布动作。

## 8. 商业与运营约束

- 模型和算力成本必须按 tenant/task/attempt 归因并有硬预算。
- 生产数据不得发送给未批准的模型或地区。
- 企业客户要求可配置保留期、删除证明和审计导出。
- 平台需要支持模型供应商切换，业务状态不能绑定某个模型 SDK。
- 高风险动作采用默认拒绝和人工审批，审批必须记录主体、范围、时间和理由。

## 9. 发布成功标准

Internal Beta 至少需要 5 个内部团队、100 个真实任务和 30 天运行数据；任务成功率、P95 排队时间、成本、
取消时延和人工接管率达到目标；Critical/High 安全问题为零；备份恢复和 Worker 崩溃恢复演练成功。Production v1
还要求容量压测、渗透测试、隐私评审、SLO 值守和客户退出/删除流程通过。
